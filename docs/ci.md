# CI

This page describes the checks under `.github/workflows/` that run on pull requests, on pushes to main and on a schedule. The layout follows the sister project [Shadewright](https://github.com/shadewright-labs/shadewright).

## Pull requests and pushes to main

`ci.yml` runs on pull requests, pushes to main and by hand, and calls the workflows below. Two pull request workflows have triggers of their own (see the end of this section), and CodeQL and Scorecard also run on their own triggers (see [Scheduled runs](#scheduled-runs)). The `Changed files` job of `ci.yml` has no dependencies, like the three jobs that always run. It runs `hack/ci-changed.sh` on the files the pull request changes and sets four groups:

| Group | Runs when these change | Jobs |
| --- | --- | --- |
| go | Go code, `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `vendor/`, `cmd/`, `internal/`, `examples/`, the root `Dockerfile`, `.dockerignore`, `Dockerfile.dockerignore`, `Makefile`, `GNUmakefile`, `makefile`, `hack/`, `.golangci.yml`, `docs/reference/`, and the workflows that build Go outside `ci.yml` (`fuzz.yml`, `release.yml`) | lint, test, govulncheck, gosec |
| images | Go code, `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `vendor/`, `cmd/`, `internal/`, `examples/`, the root `Dockerfile`, `.dockerignore`, `Dockerfile.dockerignore`, `LICENSE` and `hack/setup-buildx.sh`, which the build job runs; `hack/test/ci-changed_test.sh` tests these paths, including the scripts that `images-build.yml` runs and the named `COPY` sources of the `Dockerfile` | image build (pull requests only) |
| docs | `docs/reference/`, `cmd/`, `internal/`, `Makefile`, `GNUmakefile`, `makefile` | reference pages check |
| codeql | Go code, `go.mod`, `go.sum`, workflows, composite actions under `.github/actions/`, CodeQL configuration under `.github/codeql/` | CodeQL (pull requests only) |

A change to `ci.yml`, to a workflow it calls, to `hack/ci-changed.sh` or to `hack/ci-ok.sh` selects every group, and so does a push to main or a manual run. Selecting a group does not lift a job's own event condition: in `ci.yml` the image build and CodeQL run only on pull requests. The script reads the diff as NUL-separated paths, so names with spaces, tabs, non-ASCII characters or a leading dash are classified like any other. The script tries to fetch a missing base commit, and selects every group when the diff still fails or it cannot create its temporary file. Its offline tests are `hack/test/ci-changed_test.sh`.

The Go jobs that `ci.yml` calls set `GOWORK=off`. The three Dockerfiles that run `go` (the root `Dockerfile`, `cmd/sablecourt-agent/Dockerfile` and `examples/demo-agent/Dockerfile`) set `ENV GOWORK=off` in the build stage. `hack/check-dockerfiles.sh` reads each Dockerfile line by line and fails a stage in which a `RUN` line calls `go` before the `ENV GOWORK=off` line. It does not join lines continued with a backslash, so a `go` call on a continuation line is not seen.

Besides the root `Dockerfile` there are four nested Dockerfiles: `cmd/sablecourt-agent/Dockerfile`, `examples/demo-agent/Dockerfile`, `internal/gate/councilproxy/Dockerfile` and `internal/harnessimages/Dockerfile`. The last one is embedded in the Go package `internal/harnessimages`, and `sablectl harness build <role>` builds the harness images from it. CI builds only the root `Dockerfile`. A change to a nested one selects the groups of its directory, and Dependabot is configured to check their base images weekly.

The groups call these workflows:

- `lint.yml` (go): `go mod tidy -diff`, then golangci-lint through `make -f Makefile lint-config` and `make -f Makefile lint`. The configuration is `.golangci.yml`, which enables a chosen set of linters; a comment at its end gives the reason for leaving out several others.
- `test.yml` (go): `go vet ./...`, `go test -race -count=1 -covermode=atomic -coverprofile=coverage.out ./...` (which also runs the tests of the generated reference pages), a 10 second fuzz run of the Model Gate SSRF guard, a build of `sablecourtd`, `sablectl`, `sablecourt-agent` and `examples/demo-agent`, and `sablectl validate` on `examples/local-demo.yaml`. The coverage profile goes up as an artifact. A second job, `coverage upload`, runs only after the test job succeeded and sends the profile to Codecov with the pinned `codecov/codecov-action` and uploader version. `ci.yml` passes it only the secret `CODECOV_TOKEN`. When the token is empty, the job prints a notice and passes without uploading. The upload step sets `fail_ci_if_error: false`, so an upload error that the action handles does not fail the job; a failure of the checkout, the artifact download or the action itself does. `codecov.yml` makes the project and patch statuses informational, so the coverage figures do not block a merge. `ci-ok` sees one result for `test.yml`: if the tests fail, the upload is skipped and `test` fails; if the upload job fails, `test` fails too.
- `vulncheck.yml` (go): `make -f Makefile vulncheck` (govulncheck, version pinned in the Makefile). It also runs every Monday and can be started by hand.
- `gosec.yml` (go): gosec v2.30.0 with G104, G304 and G204 excluded, on the Linux build. The job also fails when gosec's output matches one of its load or analysis error patterns, or reports zero files, even if gosec exits 0.
- `images-build.yml` (images): builds the `daemon` and `agent` targets of the root `Dockerfile` for linux/amd64 without pushing, with the pinned Buildx and BuildKit of `hack/setup-buildx.sh`.
- `docs-check.yml` (docs): `make -f Makefile docs-check`, which runs the tests that compare the reference pages under `docs/reference/` with the code.
- `codeql.yml` (codeql): CodeQL for Go and for the workflows. It also runs on pushes to main, every Monday and by hand.

Three jobs of `ci.yml` run on every pull request, whatever changed:

- `repo-checks.yml`: `python3 -I hack/docs-links.py check`, which reads the tracked Markdown files, reports full and collapsed reference links with no definition, checks that linked local files exist and checks heading fragments in Markdown files. It recognises inline links, angle-bracket links, full and collapsed reference links, the `href` and `src` of `<a>` and `<img>`, and headings in both the `#` and the underlined (Setext) form. It skips fenced code blocks and code spans, but it reads a fence inside a block quote as ordinary text. It does not follow shortcut reference links (`[text]` alone). Links to pages or headings not written yet are listed in `hack/docs-pages-pending.txt` as `<source> -> <target>[#fragment]`. Each line covers one link, and each use of a reference link counts as one link, so two links from one page to the same pending target need two lines. The check fails when a target exists or a line is no longer used, so remove the lines in the pull request that adds the page. The same job runs `hack/check-image-refs.sh`, which searches tracked text for the full prefix `ghcr.io/shadewright-labs/` and leaves out its own script and test. It fails on an image name other than `sablecourt` and `sablecourt-agent`, on a tag other than `X.Y.Z`, `X.Y.Z-rc.N` and `latest` (such as `v0.1.0` or an empty tag), and on a digest, alone or after a tag, that is not `sha256:` and 64 lower-case hex digits. `release.yml` accepts the same two version forms. The job also runs `hack/check-dockerfiles.sh` and thirteen of the offline suites under `hack/test/` (the fourteenth, `gitleaks_test.sh`, runs in `secret-scan.yml`). One of them, `workflows_test.sh`, searches the workflow text for the two action names `docker/setup-buildx-action` and `anchore/sbom-action`, in each shell script under `hack/` compares the number of checksum commands with the number of lines that start with `curl`, checks that every action is pinned by commit with its version in a comment, and checks the structure of `release.yml` (see [Releases](#releases)).
- `workflow-lint.yml`: actionlint, shellcheck over `hack/*.sh` and `hack/test/*.sh`, and zizmor over `.github/workflows`. zizmor is installed with `pip --require-hashes` from `hack/zizmor-requirements.txt`.
- `secret-scan.yml`: gitleaks with the default rules plus `.gitleaks.toml`, over every ref and the full history of the checkout (`fetch-depth: 0`), including the changes that only a merge commit introduces (`hack/secret-scan.sh` passes `--diff-merges=first-parent`).

gitleaks ignores the exit status of the `git log` it runs, so `hack/secret-scan.sh` adds its own checks. It reads the same range first and fails when that `git log` or `git rev-list` fails, or when the log does not list exactly the commits `git rev-list --count` counts. It then runs gitleaks with a small `git` wrapper first in `PATH`, which records the exit status of each `git log` that gitleaks starts through `PATH`; the scan fails when one of them exits non-zero or when none was recorded. Last, it fails when gitleaks reports fewer scanned commits than the history has commits with a text change in a file that is not deleted. Known limit: a `git log` that stops part way through a commit and still exits 0 is not detected, because gitleaks counts commits and not bytes.

The test fixtures that this change edited are joined from split strings, so stock gitleaks finds nothing in them. The history still holds their earlier literals. Sixteen of the 17 entries of `.gitleaks.toml` each allow one exact value, anchored at both ends, in one file and only in the listed commits, so the same value in a new commit is reported. The 17th entry, for `internal/gate/mcp/upstream_test.go`, lists no commits: that file still holds its fake token as a literal, because this change leaves `internal/gate` as it is. It allows that one token in that one file in any commit, and no other value. Before the scan, `hack/test/gitleaks_test.sh` runs the same script on throwaway repositories. Its cases are: a token in an ordinary file, a key block or token added before or after the current fixtures, new content at the three paths only the history holds, a commit-scoped value in a new commit, and tokens added only in a merge commit. It also checks that each entry has one value and, except the one above, names commits, and that four kinds of broken history read fail the scan (a failed `git log` of the script, a failed or empty `git log` of gitleaks, and one cut short inside the last commit). A commit-scoped fixture value that comes back at its original path in a new commit is reported, so a branch made before this change that adds one again needs a rebase on main. The exact token of the unscoped entry stays allowed at its path.

The last job, `ci-ok`, needs all of them and runs `hack/ci-ok.sh` on their results. It passes only when `Changed files` succeeded and each of its four outputs is exactly `true` or `false`, every job that the groups and the event select succeeded, and every job that always runs succeeded. A job counts as legitimately skipped only when its group is `false` or the event excludes it. A job missing from the results, a selected job that was skipped, and any failure or cancellation fail `ci-ok`. It sees the result of each called workflow, not the steps inside it, so a check removed from a called workflow that still succeeds goes unnoticed there. Its tests are `hack/test/ci-ok_test.sh`, which also checks that the job list in the script matches the `needs` of `ci-ok`. A new run for a pull request cancels the run in progress for the same pull request. Runs on main are grouped by commit and do not cancel a run in progress.

Two more workflows run on pull requests outside `ci.yml`. `dependency-review.yml` (job `Dependency review`) is configured to fail on a new or bumped dependency with a known vulnerability of moderate severity or higher, or with one of ten licences named by exact SPDX identifier: GPL-2.0, GPL-3.0, AGPL-3.0, LGPL-2.1 and LGPL-3.0, each in its `-only` and `-or-later` form. `pr-title.yml` (job `Conventional PR title`) checks the title against Conventional Commits: an allowed type, a scope from its list if there is one, and a summary of at least two characters that starts with a lower-case letter and does not end with a full stop. It runs on `pull_request_target`, so GitHub takes the workflow from the base branch, not from the pull request.

Every workflow except `pr-title.yml` starts with `permissions: {}` and grants each job its own permissions; `pr-title.yml` grants `pull-requests: read` at workflow level and has no checkout step. Every checkout step sets `persist-credentials: false`, and every action from another repository is pinned to a full commit SHA. The executables that a job downloads itself (actionlint, gitleaks, Buildx, syft, Trivy) are checked against a sha256 kept in the file that installs them, and the BuildKit image is pinned by digest. Actions and tools may download further components of their own.

### Required checks

The checks that block a merge are a repository setting: the branch ruleset for main. No file in this repository sets or checks it, so this section describes a plan, not something the workflows enforce. The intended required checks are `ci-ok`, `Conventional PR title` and `Dependency review`. The old `ci.yml` had the jobs `verify` and `security`; while the ruleset still requires them, a pull request on this layout cannot satisfy it.

### Switching the required checks

The pull request that brings this layout removes the jobs `verify` and `security`, so it never reports them. If the ruleset still requires them when it is ready, the switch goes in this order:

1. When the pull request is ready to merge, a repository admin changes the ruleset's required checks to `ci-ok` and `Dependency review`, and merges.
2. `Conventional PR title` runs from the base branch (`pull_request_target`), and `pr-title.yml` does not exist on main before this change, so the check cannot report on this pull request. Add it to the required checks only after this change is on main.

## Scheduled runs

| Workflow | When | What |
| --- | --- | --- |
| `vulncheck.yml` | Mondays, by hand | govulncheck |
| `codeql.yml` | Mondays, pushes to main, by hand | CodeQL for Go and workflows |
| `scorecard.yml` | Mondays, pushes to main, branch protection changes, by hand | OpenSSF Scorecard, results to the Security tab |
| `fuzz.yml` | Tuesdays, by hand | one job per fuzz target that `hack/fuzz-targets.sh` lists, each asking for 4 minutes of fuzzing; on failure or cancellation, later steps try to collect and upload new corpus files that Git does not ignore |
| `docs-links.yml` | Wednesdays, by hand | reports external links that do not answer, as warnings; a dead link does not fail the job |

`hack/fuzz-targets.sh` takes its list from `go test -list '^Fuzz' ./...`, so a target with an unnamed parameter, a signature over several lines or an alias of `testing` is listed like any other. It keeps the names made of ASCII letters, digits and underscores; a target with another letter in its name is not run. It sees the files that build on linux/amd64 with no extra build tags, and it fails when `go test` fails or no name is left. `hack/fuzz-failures.sh` copies the untracked files that Git does not ignore under `testdata/fuzz/` at the module root and in nested packages, keeping their paths. Dependabot (`.github/dependabot.yml`) is configured to check Go modules, GitHub Actions and the base images of the five Dockerfile directories weekly. The base images of the root `Dockerfile` are pinned by tag and digest.

## Releases

`release.yml` runs on a pushed `v*` tag and has no other trigger. A run builds four archives, `sablecourt_<version>_<os>_<arch>.tar.gz` for darwin and linux on amd64 and arm64, each with `sablecourtd` and `sablectl`, and the `daemon` and `agent` images for linux/amd64 and linux/arm64, pushed to `ghcr.io/shadewright-labs/sablecourt` and `ghcr.io/shadewright-labs/sablecourt-agent`. A release has fourteen files: the four archives; five SPDX SBOMs (`sablecourt_<version>_sbom.spdx.json` for the eight binaries and `sablecourt_<version>_image_<image>_linux_<arch>.spdx.json` for each platform image); `checksums.txt` with the sha256 of those nine files; `checksums.txt.sigstore.json`, the cosign signature bundle of `checksums.txt`; and three build provenance bundles, `sablecourt_<version>_provenance.intoto.jsonl` for the nine files and `checksums.txt`, and `sablecourt_<version>_image_<image>.intoto.jsonl` for each image index. The `.sigstore.json` and `.intoto.jsonl` endings were chosen for OpenSSF Scorecard's Signed-Releases check.

A job starts only when every job in its `needs` has succeeded; no job or step has an `if:` or `continue-on-error`. The `needs` of each job:

| Job | Needs |
| --- | --- |
| `check` | nothing |
| `binaries` | `check` |
| `images` | `check` |
| `scan-images` | `images` |
| `sign-images` | `check`, `binaries`, `images`, `scan-images` |
| `sign-binaries` | `check`, `binaries`, `scan-images`, `sign-images` |
| `verify` | `check`, `images`, `sign-binaries`, `sign-images` |
| `publish` | `check`, `binaries`, `images`, `scan-images`, `verify` |

So no signing job starts unless `check`, both builds and the scan passed, and no release or image tag is written unless `verify` passed. Nothing is signed for a tag whose scan fails, archives included: the release could not be published anyway, and so the transparency log holds no signature from this workflow for a tag that was not released.

1. `check` (contents: read, checks: read, actions: read) refuses a tag that is not `vX.Y.Z` or `vX.Y.Z-rc.N` and a tagged commit that is not an ancestor of the fetched `origin/main`. `hack/release-state.sh` lists the releases of the repository and stops the run when the tag has a published release, when the lookup fails, and when the answer is empty or is not a list of releases. `hack/release-ci-ok.sh` reads the workflow runs of the tagged commit (`actions/runs?head_sha=<sha>&event=push&branch=main`) and its `ci-ok` check runs, and keeps only the runs of `.github/workflows/ci.yml` with the event `push`, the branch `main`, this commit, and this repository as both the repository and the head repository, whatever the query returned. The newest of those runs (highest run id) decides: it must be completed with success, and the newest `ci-ok` check run of the github-actions app in that run's check suite must be completed with success too. A newer run that failed wins over an older one that passed, because it is the latest result for the commit and a release does not pick the run it likes. No such run, a run or check still queued or in progress, any other conclusion, a list longer than one page, or an answer it cannot read stops the release with the reason. Its table tests use recorded answers, among them a pull request from a fork whose branch is called `main`.
2. `binaries` (contents: read) runs `hack/package-binaries.sh`: `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false`, the version stamped into `sablectl` (piped, `sablectl version` prints `sablectl <version>`), and archives packed by `hack/targz.go` with the same Go toolchain (entries sorted, owner 0:0, mode 0755, time and gzip header time from the commit time, `SOURCE_DATE_EPOCH`). `setup-go` runs with `cache: false`, so it restores and saves no cache. The job summary and the release notes record the Go version. Syft, installed by `hack/install-syft.sh` at a pinned version and sha256, writes the SBOM of the binaries. Beside it, `images` (contents: read, packages: write) builds both images with the pinned Buildx and BuildKit of `hack/setup-buildx.sh` and pushes them by digest; it sets no tag.
3. `scan-images` (contents: read, packages: read) scans each platform image of both images by digest with Trivy, installed by `hack/install-trivy.sh` at the version and sha256 the sister project pins. See [Scan policy](#scan-policy).
4. `sign-images` (contents: read, packages: write, id-token: write, attestations: write) signs each image index by digest with cosign keyless, attaches an SPDX SBOM made by syft from each platform image as a signed attestation on that image's digest, keeps the same SBOM file for the release, and stores build provenance for each index in the registry and as an `.intoto.jsonl` file. `sign-binaries` (contents: read, id-token: write, attestations: write) writes `checksums.txt` over the archives and the five SBOMs, signs it with cosign keyless (bundle `checksums.txt.sigstore.json`) and records one build provenance attestation for the nine files and `checksums.txt`, also kept as `sablecourt_<version>_provenance.intoto.jsonl`.
5. `verify` (contents: read, packages: read, attestations: read) runs the checks of [Verify a release](how-to/verify-a-release.md) on the run's artifacts and on the digests `images` reported, not on a published release: it checks that the files are exactly the fourteen expected names, then verifies them with the exact certificate identity `https://github.com/shadewright-labs/sablecourt/.github/workflows/release.yml@refs/tags/<tag>` (cosign `--certificate-identity`, gh `--cert-identity`) and the GitHub OIDC issuer. Each of its four `gh attestation verify` commands passes `--source-ref` and `--source-digest` for this tag and commit and `--deny-self-hosted-runners`; each runs once against GitHub's attestation API and once against the `.intoto.jsonl` file of the release. It also requires nine lines in `checksums.txt`, exactly one child image per architecture, and each image SBOM file to equal the predicate of one of the verified attestations on that platform image. Last, it removes the GHCR login and runs the stamped linux/amd64 `sablectl version` with an empty environment and an empty home, and requires the output to be exactly `sablectl <version>`. `GH_TOKEN` is set only on the two steps that call `gh`.
6. `publish` (contents: write, packages: write, environment `release`) is the one job that writes a release or an image tag. Before it writes anything it stops when the tag no longer points at the commit of the run, when `hack/release-state.sh` finds a published release or cannot read the list, and when `hack/release-image-tag.sh` finds a version image tag on another digest or cannot read it. A tag that does not exist counts as absent only when Buildx exits 1, prints nothing on standard output and prints exactly one line, `ERROR: <image>:<tag>: not found`; any other failure stops the job. It then decides with `hack/release-latest.sh` whether this release moves `latest`, deletes every draft release of the tag that its token can see, including one made by hand (the release only, not the Git tag), creates a draft with `gh release create --verify-tag` and the fourteen files, and checks the draft with `hack/release-assets.sh`: the same names, no extra asset, and every asset, downloaded again, equal to the verified file. It adds the version tag to both image digests (reading the tag again right before), then `latest` when this release moves it, and reads each tag back to compare its digest. It then publishes the draft: as a pre-release for `X.Y.Z-rc.N`, as the latest release when it moves `latest`, and with `--latest=false` otherwise. Last, it runs the asset check again.

`latest` (the image tag and the release's latest flag) moves for a full release `X.Y.Z` that is the highest full release among the repository's `v*` tags when `publish` reads them, compared as numbers (0.10.0 is above 0.9.0). Release candidates do not move it and do not count as higher. A full release tag that exists but was not published, for example after a failed run, still counts as higher. The tests are `hack/test/release-latest_test.sh`.

The workflow has `permissions: {}` at the top, and one concurrency group, `release`, for every tag, with `cancel-in-progress: false`, so runs of two tags do not overlap and two runs do not write `latest` at the same time. Each run decides `latest` again from the tags it reads. A run that waits in the group can be cancelled by GitHub when another tag is pushed; check the Actions tab after pushing tags close together and rerun a cancelled run. Every action is pinned by commit, and `sigstore/cosign-installer` installs a pinned cosign release.

### Scan policy

The policy is the one of Shadewright's Trivy gate: a HIGH or CRITICAL vulnerability fails the scan whether a fixed version exists or not, and a non-zero exit of Trivy, a scanner error included, fails it too. The project's rule is that a finding is accepted only by an entry in `.trivyignore.yaml` with its id, a `statement` of why it does not apply or is accepted, and an `expired_at` date, added in a reviewed pull request; the workflow passes the file to Trivy and does not check those fields or the review. It reads the file from the tagged commit, so a changed file needs a new commit on main and, under the project's tag rules, a new tag. The job holds no signing or write permission.

The vulnerability database is pinned by digest: the scan job sets `TRIVY_DB` to `ghcr.io/aquasecurity/trivy-db@sha256:<digest>` and passes it to `--db-repository`, so every scan of a release reads the same database, and the job summary records the database reference and its build time. The database decides what the scan can find. An old database misses vulnerabilities published after it was built, and a wrong one could hide findings or report false ones and block a release. The scan job has read permissions only, so the database gives it no way to write; what it can do is let a vulnerable image through the gate or stop the release. If the pinned digest is no longer in the registry, the download fails and the scan fails with it. To update the pin, in a pull request: run `docker buildx imagetools inspect ghcr.io/aquasecurity/trivy-db:2`, copy the `Digest:` line into `TRIVY_DB` in `release.yml`, and check that `trivy image --download-db-only --db-repository ghcr.io/aquasecurity/trivy-db@<digest>` downloads it. Update it before each release candidate. The pin covers the vulnerability database; Trivy's separate Java index database, used for Java archives, is not pinned.

When the scan fails on a tag: no signature, attestation, release or image tag exists for that tag, only untagged image digests (see the next section). Fix the finding on main, by a dependency or base image update or an accepted entry in `.trivyignore.yaml`, and cut the next release candidate from the new commit. Do not reuse the tag: leave the failed tag as it is and give the next candidate the next number. The workflow does not check this; `check` only refuses a tag that already has a published release.

### When a run fails

The table shows what can exist outside the run when one job fails, derived from the `needs` above: a job that does not need the failed job, directly or through another job, can still run and finish, and the failed job itself may have done part of its work. "Untagged image digests" are the images `images` pushed, in GHCR with no tag. "Image signatures" stand for the cosign signatures, SBOM attestations and provenance of the images, in GHCR, the Sigstore transparency log and GitHub's attestation store; the signature of `checksums.txt` and the provenance of the release files go to the transparency log and the attestation store. Run artifacts (kept for 7 days) are left out. `hack/test/workflows_test.sh` derives the same rows from `release.yml` and fails when this table differs.

| Job that failed | Can exist from the other jobs | Can exist in part from the failed job |
| --- | --- | --- |
| `check` | nothing | nothing |
| `binaries` | untagged image digests in GHCR | nothing |
| `images` | nothing | untagged image digests in GHCR |
| `scan-images` | untagged image digests in GHCR | nothing |
| `sign-images` | untagged image digests in GHCR | image signatures, SBOM attestations and image provenance |
| `sign-binaries` | untagged image digests in GHCR; image signatures, SBOM attestations and image provenance | the signature of `checksums.txt` and the provenance of the release files |
| `verify` | untagged image digests in GHCR; image signatures, SBOM attestations and image provenance; the signature of `checksums.txt` and the provenance of the release files | nothing |

When `publish` fails, everything above can exist, and what it wrote depends on the step, in this order:

| Step of `publish` that failed | What `publish` can have written |
| --- | --- |
| up to "Decide whether this release moves latest" | nothing |
| "Remove the drafts of earlier runs" | some drafts of this tag deleted |
| "Create the draft release" or "Check the draft's assets byte for byte" | a draft release, possibly with only part of its files |
| "Tag the verified image digests" | a draft, and some of the version and `latest` tags on the verified digests |
| "Publish the release" | a draft or a published release, and the image tags |
| "Check the published assets byte for byte" | a published release and its image tags |

A rerun of the failed jobs or of all jobs goes through the same gates again. What the workflow checks on a rerun:

- `check` (on a rerun of all jobs) and `publish` stop when the tag has a published release.
- `publish` stops before deleting drafts when a version image tag points at a digest other than the one this attempt verified. A rerun of all jobs builds the images again; when the new digests differ from the ones an earlier attempt tagged, it stops there, and finishing needs a new tag or the version tags removed from GHCR by hand. A version tag on the same digest is accepted.
- `publish` uploads the files that `verify` checked in the same attempt and tags the digests it verified. A rerun of failed jobs can take archives and images from different attempts of the same run; both come from the tagged commit and are verified together before `publish`.
- A scan of the same digests reads the same `.trivyignore.yaml` and the same pinned database.

If `publish` fails after writing `latest`, that tag can point at images whose release is still a draft. A difference found by the last asset check, after publication, needs a person to look at the release. GitHub's immutable releases, a repository setting, would block changes to published release assets.

### Tests

`hack/test/workflows_test.sh` checks this structure in the job and the step each property belongs to: the per-job permissions and `needs`, facts derived from the `needs` graph (no job with signing permission or a cosign or provenance step runs before `check`, both builds and the scan passed, and a signing job needs `scan-images` itself; `publish` is the only job that writes a release or an image tag, and it runs after `verify`; the failure table above), the exact ordered step names of `sign-images`, `sign-binaries`, `verify` and `publish`, the checks of `check`, push, scan and signing by digest, the pinned Trivy database, the SBOMs and provenance files, the file set, the verify commands with the exact identity, the issuer, the commit and the runner, the token-free `sablectl` step, the order of the refusals, draft, asset check, image tags and publication in `publish`, the `latest` rule, the environment, and `persist-credentials: false` on every checkout. For each check it also edits a copy of `release.yml` to remove or weaken the property and requires that the check fails; it prints the number of these mutation cases. `hack/test/package-binaries_test.sh` builds twice and compares the bytes, compares a clean copy of the tree with the same tree plus an untracked text file, and packs with a `python3` that fails. `hack/test/release-assets_test.sh`, `release-state_test.sh` and `release-image-tag_test.sh` run their scripts against a stub `gh` or `docker`, and `release-ci-ok_test.sh` and `release-latest_test.sh` are table tests of the two decisions.

Reproducible here means: in the test, the same commit built for the same targets with the same release version, Go toolchain version and `SOURCE_DATE_EPOCH` gave the same archive bytes, also with an untracked text file added. An untracked `.go` file in a built package would change the binaries. The gzip step uses Go's `compress/gzip`, so no zlib build decides the bytes. It does not cover the SBOMs (syft writes a creation time), the signatures and provenance (they hold times and certificates) or the images.

### Trust anchor and limits

The signing identity says "`release.yml` on the tag `<tag>` of this repository". It does not say who pushed the tag, and it does not say what that `release.yml` checked: the identity names the workflow path and the tag, not the content of the file, so a `release.yml` on a tagged commit that lacks the checks above would sign with the same identity. The trust anchor is therefore the repository's tag ruleset, which must limit who may create `v*` tags; the ruleset is a repository setting, and no file here shows or enforces it. A cautious user can check that the attested source commit is on main ([Verify a release](how-to/verify-a-release.md#check-that-the-commit-is-on-main)).

Not pinned by a checksum kept in this repository: the Go toolchain that `actions/setup-go` installs from the version in `go.mod`, the runner's `gh`, `jq` and Docker, and the Buildx preinstalled on the runner, which `scan-images`, `sign-images` and `verify` use for `docker buildx imagetools inspect` (the `images` and `publish` jobs install the pinned Buildx of `hack/setup-buildx.sh`). The Trivy database is pinned by digest (see [Scan policy](#scan-policy)), not by a checksum in a file.

Open items that this change leaves to the repository settings or to a later change:

- this change adds no protection rule to the `release` environment; a maintainer adds required reviewers in the repository settings;
- creating stable `vX.Y.Z` tags should be limited to a release GitHub App; until then the tag ruleset must limit `v*` tags to repository admins;
- the workflow does not check a tag signature; requiring signed tags is left for a later change, once the first release shows how tags are made;
- immutable releases are not turned on by this change.
