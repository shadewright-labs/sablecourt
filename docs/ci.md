# CI

This page describes the checks under `.github/workflows/` that run on pull requests, on pushes to main and on a schedule. The layout follows the sister project [Shadewright](https://github.com/shadewright-labs/shadewright).

## Pull requests and pushes to main

`ci.yml` runs on pull requests, pushes to main and by hand, and calls the workflows below. Two pull request workflows have triggers of their own (see the end of this section), and CodeQL and Scorecard also run on their own triggers (see [Scheduled runs](#scheduled-runs)). The `Changed files` job of `ci.yml` has no dependencies, like the three jobs that always run. It runs `hack/ci-changed.sh` on the files the pull request changes and sets four groups:

| Group | Runs when these change | Jobs |
| --- | --- | --- |
| go | Go code, `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `vendor/`, `cmd/`, `internal/`, `examples/`, the root `Dockerfile`, `.dockerignore`, `Dockerfile.dockerignore`, `Makefile`, `GNUmakefile`, `makefile`, `hack/`, `.golangci.yml`, `docs/reference/`, and the workflows that build Go outside `ci.yml` (`fuzz.yml`, `release.yml`) | lint, test, govulncheck, gosec |
| images | Go code, `go.mod`, `go.sum`, `go.work`, `go.work.sum`, `vendor/`, `cmd/`, `internal/`, `examples/`, the root `Dockerfile`, `.dockerignore`, `Dockerfile.dockerignore`, `LICENSE` and `hack/setup-buildx.sh`, which the build job runs; `hack/test/ci-changed_test.sh` tests these paths, including the scripts that `images-build.yml` runs and the named `COPY` sources of the `Dockerfile` | image build (pull requests only) |
| docs | `docs/reference/`, `cmd/`, `internal/`, `Makefile`, `GNUmakefile`, `makefile` | reference pages check |
| codeql | Go code, `go.mod`, `go.sum`, workflows, composite actions under `.github/actions/`, CodeQL configuration under `.github/codeql/` | CodeQL (pull requests only) |

A change to `ci.yml`, to a workflow it calls, to `hack/ci-changed.sh` or to `hack/ci-ok.sh` selects every group, and so does a push to main or a manual run. Selecting a group does not lift a job's own event condition: in `ci.yml` the image build and CodeQL run only on pull requests. The script reads the diff as NUL-separated paths, so names with spaces, tabs, non-ASCII characters or a leading dash are classified like any other. A missing base commit, a failed `git diff` or a failed temporary file selects every group. Its offline tests are `hack/test/ci-changed_test.sh`.

The Go jobs that `ci.yml` calls set `GOWORK=off`. The three Dockerfiles that run `go` (the root `Dockerfile`, `cmd/sablecourt-agent/Dockerfile` and `examples/demo-agent/Dockerfile`) set `ENV GOWORK=off` in the build stage. `hack/check-dockerfiles.sh` fails a stage with a shell-form `RUN` that calls `go` before that line, reading lines continued with a backslash as one instruction.

Besides the root `Dockerfile` there are four nested Dockerfiles: `cmd/sablecourt-agent/Dockerfile`, `examples/demo-agent/Dockerfile`, `internal/gate/councilproxy/Dockerfile` and `internal/harnessimages/Dockerfile`. The last one is embedded in the Go package `internal/harnessimages`, and `sablectl harness build <role>` builds the harness images from it. CI builds only the root `Dockerfile`. A change to a nested one selects the groups of its directory, and Dependabot is configured to check their base images weekly.

The groups call these workflows:

- `lint.yml` (go): `go mod tidy -diff`, then golangci-lint through `make -f Makefile lint-config` and `make -f Makefile lint`. The configuration is `.golangci.yml`, which enables a chosen set of linters; a comment at its end gives the reason for leaving out several others.
- `test.yml` (go): `go vet ./...`, `go test -race -count=1 -covermode=atomic -coverprofile=coverage.out ./...` (which also runs the tests of the generated reference pages), a 10 second fuzz run of the Model Gate SSRF guard, a build of `sablecourtd`, `sablectl`, `sablecourt-agent` and `examples/demo-agent`, and `sablectl validate` on `examples/local-demo.yaml`. The coverage profile goes up as an artifact. A second job, `coverage upload`, runs only after the test job succeeded and sends the profile to Codecov with the pinned `codecov/codecov-action` and uploader version. `ci.yml` passes it only the secret `CODECOV_TOKEN`. When the token is empty, the job prints a notice and passes without uploading. The upload step sets `fail_ci_if_error: false`, so an upload error that the action handles does not fail the job; a failure of the checkout, the artifact download or the action itself does. `codecov.yml` makes the project and patch statuses informational, so the coverage figures do not block a merge. `ci-ok` sees one result for `test.yml`: if the tests fail, the upload is skipped and `test` fails; if the upload job fails, `test` fails too.
- `vulncheck.yml` (go): `make -f Makefile vulncheck` (govulncheck, version pinned in the Makefile). It also runs every Monday and can be started by hand.
- `gosec.yml` (go): gosec v2.30.0 with G104, G304 and G204 excluded, on the Linux build. The job also fails when gosec's output matches one of its load or analysis error patterns, or reports zero files, even if gosec exits 0.
- `images-build.yml` (images): builds the `daemon` and `agent` targets of the root `Dockerfile` for linux/amd64 without pushing, with the pinned Buildx and BuildKit of `hack/setup-buildx.sh`.
- `docs-check.yml` (docs): `make -f Makefile docs-check`, which runs the tests that compare the reference pages under `docs/reference/` with the code.
- `codeql.yml` (codeql): CodeQL for Go and for the workflows. It also runs on pushes to main, every Monday and by hand.

Three jobs of `ci.yml` run on every pull request, whatever changed:

- `repo-checks.yml`: `python3 -I hack/docs-links.py check`, which reads each tracked Markdown file paragraph by paragraph and fails on a relative link to a missing file or heading, and on a reference link with no definition. It follows inline links (also over several lines, with a title in double quotes, single quotes or parentheses), angle-bracket links, full and collapsed reference links, and `href` and `src` of `<a>` and `<img>` in any quoting; it skips fenced code blocks and code spans, and headings count in both the `#` and the underlined (Setext) form. It does not follow shortcut reference links (`[text]` alone). Links to pages or headings not written yet are listed in `hack/docs-pages-pending.txt` as `<source> -> <target>[#fragment]`. Each line covers one link, and each use of a reference link counts as one link, so two links from one page to the same pending target need two lines. The check fails when a target exists or a line is no longer used, so remove the lines in the pull request that adds the page. The same job runs `hack/check-image-refs.sh` on references to `ghcr.io/shadewright-labs/` written out in full in tracked files. It fails on an image name other than `sablecourt` and `sablecourt-agent`, on a tag other than `X.Y.Z`, `X.Y.Z-rc.N` and `latest` (such as `v0.1.0` or an empty tag), and on a digest, alone or after a tag, that is not `sha256:` and 64 lower-case hex digits. That tag list is a policy for references in this repository; it is narrower than the tags `release.yml` would push for some `v*` tags, such as `v0.1.0-beta.1`. The job also runs `hack/check-dockerfiles.sh` and seven of the offline suites under `hack/test/` (the eighth, `gitleaks_test.sh`, runs in `secret-scan.yml`). One of them, `workflows_test.sh`, checks that no workflow uses `docker/setup-buildx-action` or `anchore/sbom-action` and that each `hack/*.sh` script with a `curl` line also runs `sha256sum --check --strict`.
- `workflow-lint.yml`: actionlint, shellcheck over `hack/*.sh` and `hack/test/*.sh`, and zizmor over `.github/workflows`. zizmor is installed with `pip --require-hashes` from `hack/zizmor-requirements.txt`.
- `secret-scan.yml`: gitleaks with the default rules plus `.gitleaks.toml`, over every ref and the full history of the checkout (`fetch-depth: 0`), including the changes that only a merge commit introduces (`hack/secret-scan.sh` passes `--diff-merges=first-parent`).

gitleaks ignores the exit status of the `git log` it runs, so `hack/secret-scan.sh` adds its own checks. It reads the same range first and fails when that `git log` or `git rev-list` fails, or when the log does not list exactly the commits `git rev-list --count` counts. It then runs gitleaks with a small `git` wrapper first in `PATH`, which records the exit status of each `git log` that gitleaks starts; the scan fails when one of them exits non-zero (a read cut short inside a commit) or when gitleaks ran no `git log`. Last, it fails when gitleaks reports fewer scanned commits than the history has commits with a text change in a file that is not deleted.

The test fixtures that this change edited are joined from split strings, so stock gitleaks finds nothing in them. The history still holds their earlier literals. Sixteen of the 17 entries of `.gitleaks.toml` each allow one exact value, anchored at both ends, in one file and only in the listed commits, so the same value in a new commit is reported. The 17th entry, for `internal/gate/mcp/upstream_test.go`, lists no commits: that file still holds its fake token as a literal, because this change does not edit Go code under `internal/`. It allows that one token in that one file in any commit, and no other value. Before the scan, `hack/test/gitleaks_test.sh` runs the same script on throwaway repositories. It checks that these cases are found: a token in an ordinary file, a key block or token added before or after the fixtures of each file the allowlists name, an allowed value in a new commit, and a token added only in a merge commit. It also checks that each entry has one value and, except the one above, names commits, and that four kinds of broken history read fail the scan (a failed `git log` of the script, a failed or empty `git log` of gitleaks, and one cut short inside the last commit). A branch made before this change that adds one of the old fixture literals again in a new commit is reported; rebase it on main.

The last job, `ci-ok`, needs all of them and runs `hack/ci-ok.sh` on their results. It passes only when `Changed files` succeeded and each of its four outputs is exactly `true` or `false`, every job that the groups and the event select succeeded, and every job that always runs succeeded. A job counts as legitimately skipped only when its group is `false` or the event excludes it. A job missing from the results, a selected job that was skipped, and any failure or cancellation fail `ci-ok`. It sees the result of each called workflow, not the steps inside it, so a check removed from a called workflow that still succeeds goes unnoticed there. Its tests are `hack/test/ci-ok_test.sh`, which also checks that the job list in the script matches the `needs` of `ci-ok`. `ci.yml` is configured so that a new run for a pull request cancels the older run in progress for the same pull request; runs on main do not cancel each other.

Two more workflows run on pull requests outside `ci.yml`. `dependency-review.yml` (job `Dependency review`) is configured to fail on a new or bumped dependency with a known vulnerability of moderate severity or higher, or with one of ten licences named by exact SPDX identifier: GPL-2.0, GPL-3.0, AGPL-3.0, LGPL-2.1 and LGPL-3.0, each in its `-only` and `-or-later` form. `pr-title.yml` (job `Conventional PR title`) checks the title against Conventional Commits: an allowed type, a scope from its list if there is one, and a summary of at least two characters that starts with a lower-case letter and does not end with a full stop. It runs on `pull_request_target`, so GitHub takes the workflow from the base branch, not from the pull request.

Every workflow except `pr-title.yml` starts with `permissions: {}` and grants each job its own permissions; `pr-title.yml` grants `pull-requests: read` at workflow level and has no checkout step. Every checkout step sets `persist-credentials: false`, and every action from another repository is pinned to a full commit SHA. The executables that a job downloads itself (actionlint, gitleaks, Buildx) are checked against a sha256 kept in the file that installs them, and the BuildKit image is pinned by digest. Actions and tools may download further components of their own.

### Required checks

The checks that block a merge are a repository setting: the branch ruleset for main. No file in this repository sets or checks it, so this section describes a plan, not something the workflows enforce. The intended required checks are `ci-ok`, `Conventional PR title` and `Dependency review`. The old `ci.yml` had the jobs `verify` and `security`; while the ruleset still requires them, a pull request on this layout cannot satisfy it.

### Switching the required checks

The pull request that brings this layout removes the jobs `verify` and `security`, so it never reports them. If the ruleset still requires them when it is ready, the switch goes in this order:

1. When the pull request is ready to merge, a repository admin changes the ruleset's required checks to `ci-ok` and `Dependency review`, and merges.
2. `Conventional PR title` runs from the base branch (`pull_request_target`), and `pr-title.yml` does not exist on main before this change, so the check cannot report on this pull request. Add it to the required checks only after this change is on main.

## Scheduled runs

| Workflow | When | What |
| --- | --- | --- |
| `vulncheck.yml` | Mondays, by hand | govulncheck |
| `codeql.yml` | Mondays, pushes to main, by hand | CodeQL for Go and workflows |
| `scorecard.yml` | Mondays, pushes to main, branch protection changes, by hand | OpenSSF Scorecard, results to the Security tab |
| `fuzz.yml` | Tuesdays, by hand | each fuzz target that `hack/fuzz-targets.sh` lists, for 4 minutes, one job per target; on failure or cancellation, new files under `testdata/fuzz/` are uploaded as an artifact |
| `docs-links.yml` | Wednesdays, by hand | reports external links that do not answer, as warnings; a dead link does not fail the job |

`hack/fuzz-targets.sh` takes its list from `go test -list '^Fuzz' ./...`, so a target with an unnamed parameter, a signature over several lines or an alias of `testing` is listed like any other, and so is one whose name has non-ASCII letters. It sees the files that build on linux/amd64 with no extra build tags; it fails when a package does not build or the list is empty. `hack/fuzz-failures.sh` collects the untracked files under `testdata/fuzz/` of every package, the module root included. Dependabot (`.github/dependabot.yml`) is configured to check Go modules, GitHub Actions and the base images of the five Dockerfile directories weekly. The base images of the root `Dockerfile` are pinned by tag and digest.

## Releases

`release.yml` runs on a pushed `v*` tag, or by hand with a version. It builds `sablecourtd` and `sablectl` for darwin and linux (amd64 and arm64) into four `sablecourt_<version>_<os>_<arch>.tar.gz` archives, publishes them with `checksums.txt` as a GitHub release, and pushes the `daemon` and `agent` images to `ghcr.io/shadewright-labs/sablecourt` and `ghcr.io/shadewright-labs/sablecourt-agent`, tagged with the version without its `v` and with `latest`. The archive names, platforms, images and tags are those of the `release.yml` on main before this change. Like the other workflows it pins its actions by commit, sets permissions per job and installs Buildx with `hack/setup-buildx.sh`.

The publish step uses the `gh` client. When `gh release view` finds a release for the tag, it uploads the five files with `--clobber`, which replaces assets of the same name; the release's notes and its draft state stay as they were, so a rerun does not publish a draft. When the lookup fails for any reason, the step tries `gh release create` with generated notes.

Who may create `v*` tags is a repository setting, not something this repository's files enforce. A signed and verified release path is tracked in a follow-up issue.
